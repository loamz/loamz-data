# 0009 security and architecture review

14 November 2026. **Direction sound; not ready for a first customer.** Airflow can schedule trusted code, while Loamz authorizes and runs customer work. Valid JSON and one factory do not by themselves enforce that boundary. The operator calls a Loamz API and waits or polls; it does not run the customer's step on the Airflow host.

## Three main escape routes

1. **JSON becomes code or an Airflow control.** A template, shell expression, import path, operator name, callback, URL, file path, serialized object or unvalidated `dag_run.conf` could be evaluated by the factory or an operator. Use a closed, versioned schema with `additionalProperties: false`, fixed step types and typed fields; no dynamic imports, eval, Jinja, shell, callbacks, arbitrary API paths or user-controlled Airflow configuration. Construct a fixed operator with non-templated data and bounded validated parameters. Python steps are untrusted code executed only by Loamz in the caller-authorized gVisor job. Imports use the existing governed import path and its network/SSRF rules.
2. **A forged ID, owner or confused deputy.** Resolve every pipeline, DAG, run, step and referenced input/output by server-owned opaque IDs scoped to organization and workspace; authorize all of them for the pipeline owner on every dispatch. Never accept owner, tenant, credential, DAG ID or target API from Airflow payloads. An authenticated operator must exchange its workload identity with Loamz for a short-lived, audience-bound, single-step capability; Loamz looks up the immutable definition and current owner itself. Both a guessed ID and a forbidden object return 404. `EXECUTE` is explicit delegation to run as the owner: show that to the grantor, restrict who can grant it, and audit who triggered the run and whose rights were used. Untrusted run parameters cannot widen owner rights or redirect writes.
3. **Retries, stale definitions or leaked internals cross the boundary.** A forged trigger, stale serialized DAG, replayed capability, retry after revocation, scheduler cache, global list, logs or XCom can run or reveal another person's work. Pin each run to an immutable definition and owner generation, reauthorize on every attempt and at actual Loamz access, fence stale workers with a generation and idempotency key, and scope every list and cursor before counts, ordering and paging. Do not pass through Airflow logs, XCom, internal paths or raw errors. No data, tokens or secrets in Airflow metadata, DAG parameters, task logs or XCom.

## Candidate gateway calls

Pin **Apache Airflow 3.1.1**, its image digest, matching providers, auth manager and public API/OpenAPI schema; upgrade only with a recorded endpoint and security review. Airflow 3 uses `/api/v2`, whereas Airflow 2 used `/api/v1`; its public API uses a JWT issued by the configured auth manager. The following are candidates for individually reviewed method/path/field rules, not wildcard forwarding or a claim they have been tested with Loamz. Sources: [Airflow 3.1.1 REST reference](https://airflow.apache.org/docs/apache-airflow/3.1.1/stable-rest-api-ref.html), [Airflow 3 API authentication](https://airflow.apache.org/docs/apache-airflow/3.1.1/core-concepts/auth-manager/index.html).

- `GET /api/v2/dags` and `GET /api/v2/dags/{dag_id}`: only server-mapped, authorized DAGs. Prefer Loamz's scoped index for lists; never expose upstream totals or paging for other tenants. `PATCH /api/v2/dags/{dag_id}`: gateway builds **only** `is_paused`, after EXECUTE authorization.
- `GET` and `POST /api/v2/dags/{dag_id}/dagRuns`: list scoped runs or trigger one. Gateway creates the run ID and minimal fixed body; no arbitrary `conf`, logical date, impersonation or replay. `GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}` and `GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances`, plus `GET .../taskInstances/{task_id}`: map and authorize both run and task; return only Loamz-approved fields.
- `POST /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/clear` is **not a transparent retry**: expose only if reauthorization, pinned definition, quotas and idempotent effects are proven. `PATCH /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}` is not a reliable cancellation of already dispatched Loamz work: expose a Loamz cancellation operation that first fences new steps, cancels their Loamz runs and reconciles Airflow state. Permit only the exact upstream state update required after testing. Do not accept caller-specified states. Airflow DAG deletion, if required for cleanup, is internal only after fencing and draining.
- Never forward `/auth/*` to users; `/execution/*` is Airflow's internal worker protocol, not the public API. Deny `/ui/*`, logs and external log URLs, XCom, DAG source/import errors, connections, variables, pools, configuration, plugins, providers, users/roles, assets, backfills, task-state bulk updates, arbitrary clear and all unknown endpoints. No passthrough headers, redirects, paths, tokens, filters or `conf`. A stock Airflow client cannot be promised to work beyond this documented subset.

## Authentication and delegated work

The gateway authenticates *to Airflow*, not as the customer: retrieve a dedicated least-privilege service login from OpenBao and use the pinned auth manager's internal `POST /auth/token` to obtain a short-lived Airflow API JWT. Send it only over an authenticated private channel to the isolated API server; rotate both credential and tokens. Do not enable an all-admin/no-credential mode. The caller never gets either credential. The Airflow worker's internal execution JWT is a different credential and never authorizes Loamz.

The trusted operator authenticates *to Loamz* with its own short-lived, audience-restricted workload identity from the platform's workload identity broker (mTLS or equivalent), not an owner's stored login. Loamz verifies the identity and the dispatch record, and issues or uses a narrowly scoped, expiring capability for one pipeline generation, run, step and attempt. Bind it to the worker identity where supported; apply replay protection and rate limits. This broker, its identity issuance, and owner delegation do not exist merely because the proposal names them: they are a first-customer prerequisite. Never put credentials in definitions, Airflow connections, environment visible to task code, command lines, DAG serialization, XCom or task logs; use a protected in-memory channel, disable automatic result XCom, redact errors and test canary secrets end to end. A compromised trusted operator remains powerful; restrict network, workload identity and API permissions, and treat it as a security boundary.

## Two databases and changes in rights

- **Create:** Loamz transaction creates a non-runnable `creating` object, generation, durable operation and audit. Idempotently publish the validated definition and wait for Airflow to acknowledge that exact generation. Only then mark `active`; retry or reconcile failures without exposing an ungoverned DAG. Use a deterministic opaque DAG ID and operation ID, and handle timeout-after-success without duplicate runs.
- **Drop:** transactionally tombstone and fence the generation, reject new requests/triggers and stop schedule admission. Idempotently pause/remove the Airflow DAG, cancel and verify Loamz runs, remove definitions and mappings, then mark `dropped` with audit. Retry every external action until confirmed; a database outage or stale DAG cannot reactivate a tombstone. Define status and retry visibility for operators.
- **Erase:** fence first, then durably remove or de-identify identity, definitions, run data, alerts, Airflow metadata, logs, XCom and all derived copies; track each system and verify completion before reporting success. Specify backup expiry and restore-time tombstone replay so restores cannot resurrect work or erased content. Airflow deletion semantics, retention and supported cleanup must be proven for the pinned version; don't claim a database transaction covers both systems.
- **Owner changes and erasure:** a transfer requires authorized, explicit acceptance by the new owner and validation of all dependencies; atomically increment the owner generation and audit. Cancel or fence old-generation queued and running work; do not silently run it under the new owner. On owner erasure, disable and cancel first; no implicit admin/service-principal takeover. Keep only lawful, non-identifying audit evidence. A disabled, removed or erased owner makes the pipeline non-runnable.
- **Access loss:** recheck owner membership, compute, source and destination policies at submit, dispatch, lease, each governed data access and result retrieval. Fence further steps immediately; cancel in-flight jobs and revoke their job capabilities. A non-revocable storage credential or signed URL may remain usable until expiry: record the real bound, use short TTLs, and never promise instantaneous byte-level revocation. Hide results and logs when current access is lost. Validate what happens during authorization or identity-service outages: fail closed.

## Limits and first-customer gates

Initial ceilings, configurable downward: 50 steps and 200 edges per pipeline; 256 KiB definition; 3 retries per step with bounded exponential backoff; 1 hour per step; 2 active runs per pipeline, 10 per workspace and an organization-wide cap; 1 trigger per minute per pipeline plus workspace/org token buckets and bounded queues. Disable catchup, historical date overrides and backfill by default; enable a capped date range and run count only through a separately authorized, audited operation. Schedule minimum interval 5 minutes. Apply limits atomically across gateway replicas to schedules, retries, clears and manual triggers; bound status polling and alert delivery too.

Before a customer: demonstrate the exact pinned-client contract and no direct path to Airflow or its database; restrict egress, secrets, plugins and trusted DAG deployment; encrypt and back up both stores. Run hostile two-organization tests for IDs, bodies, lists, counts, cursors, schedules and logs; test dependency policies, owner change/erasure and mid-run revocation; prove sandbox and import boundaries. Fault-inject every cross-database transition, timeout, retry, replay, concurrent trigger, scheduler restart and restore; prove cancellation reaches Loamz jobs and quotas survive multiple replicas. Prove alert isolation, credential redaction and retention/erasure, and document the residual lifetime of already vended credentials. No first-customer claim until the operator identity broker and these tests exist.
