# loamz-data

The governed data platform of Loamz, in Rust. Docs start at `docs/README.md`: `docs/product/` (overview, requirements, roadmap), `docs/architecture/` (overview, platform, decisions), `docs/design/` (one per part), `docs/proposals/` (agreed plans with tasks). How to work on it: `CONTRIBUTING.md`. Contract: `specs/data/v1/openapi.yaml`.

## Layout

- `server/lake` (`loamz-lake`): storage library. `grants/` gives machines short-lived credentials limited to some folders: the `Issuer` trait, with `R2Issuer` (Cloudflare's API) and `StsIssuer` (STS `AssumeRole` with a session policy from `policy.rs`, signed by `sigv4.rs`: RustFS, S3). `sql.rs` is one database layer for SQLite and Postgres; `files.rs` is a folder per volume or table on a POSIX path; `objects.rs` is the `Store` the server uses: a bucket (Cloudflare R2/S3, the home of data so remote machines can query it; signed GET/PUT addresses for exactly one file) or a folder. Settings: `LOAMZ_DATA_BUCKET` + `_ENDPOINT` + `_KEY_ID_FILE` + `_SECRET_FILE`, or `LOAMZ_DATA_STORES_DIR`.
- `server/server` (`loamz-data-server`, binary `loamz-data`): the governed API.
  - `kernel/`: settings, the token check (OIDC only), errors (problem+json), the one `authz::authorize`, app state. Knows no feature.
  - `governance/{audit,orgs,workspaces,iam,catalogs,lifecycle}/`, `compute/` and `work/queries/` (saved queries: a person's own, admins see all): each has `model.rs` (pure), `service.rs` (use cases), `store.rs` (SQL), `api.rs` (HTTP). `governance/context.rs` works out what a request is about (`OrgCtx`, `WsCtx`, `FileCtx`).
  - `storage/volumes/`: the files of volumes, reached only through governance.
  - `storage/tables/`: tables are **Iceberg only**. This server is their REST catalog (`/api/v1/workspaces/{ws}/iceberg/v1/…`; the warehouse is a catalog, a namespace a schema): it checks who may load or commit, writes the metadata file, moves the pointer (`securables.metadata`) in one transaction with its audit entry, and hands the client short-lived credentials for that table's folder only. DuckDB 2.0 creates, writes and reads through it.
  - `compute/`: compute targets (a machine that connects out, or a *serverless* provider endpoint the server calls), runs (SQL statements and jobs), the agent protocol, and the scoped tokens a run carries. `compute/sql.rs` parses a statement and lists the tables it reads.
- `server/runner` (`loamz-runner agent`): a compute agent. It connects out to a Data server, leases work, fetches only what the run's token allows, runs it in a gVisor sandbox (limits written into the sandbox's own OCI config and checked before it starts), and reports. `src/sandbox/run_sql.py` is what runs a statement inside the sandbox, with DuckDB locked down. `rootfs/build.sh` builds the sandbox filesystem (Python and DuckDB); `scripts/fetch-runsc.sh` fetches gVisor. Both keep their output in `~/.cache/loamz/`.
- `web/`: the web app (React, Tailwind, Radix), served as two kinds of site from one build (`web/src/site.ts`): the **account site** (`data.loamz.com`: product page, sign-in, Home, account console) and one **site per workspace** (`w-<id>.data.loamz.com`: overview, catalog, SQL editor, compute, settings; nothing links out, only Sign out). Sign-in on a workspace site comes back through the account site's `/relay`, and the server does the Keycloak token exchange (`/api/v1/auth/token`) because Keycloak cannot allow wildcard origins. Production needs wildcard DNS and TLS for `*.data.loamz.com`, and the server serving `web/dist` (not built yet).
  - `web/src/design/` is the shared Loamz design system, copied from loamz-chat by `web/scripts/sync-design.sh`: never edit it here. Rules in `web/src/design/DESIGN.md` (primitives, tokens, orange = action, violet = selected).
  - The workspace site is a **workbench** like Databricks (`Workbench` in the design system): a top bar (the Loamz mark and "Loamz Data" on the left; theme, workspace switcher and user on the right, as in Databricks) over a labeled sidebar (Home, Catalog, Jobs, Compute; SQL: SQL editor, Queries, Query history; Settings for admins). Object pages (catalog, schema, table, volume) have a breadcrumb, line tabs, a `DataTable` sized to its content and a `DetailRail`; no page subtitles. Data screens use these, not `Page`.
  - Screens in `web/src/screens` (Workspace is Home, Catalog, SqlEditor, Queries, QueryHistory, Jobs, Run, Compute (one list: serverless and machines, each saying what it runs), Settings with a sub-nav of Members, Entitlements and Workspace); the SQL editor and Query history are loaded on demand. The SQL editor has a left pane of Catalog, Queries (saved) and History (your own statements; a click opens one in a new tab), as in Databricks. `GET /workspaces/{ws}/runs` takes `by`, `target`, `state`, `since_ms`, `before_ms` and says how long each run waited (`queued_ms`) and ran (`run_ms`).
- `deploy/dev`: the local stack (Keycloak 26.8.1 and Postgres, in docker), with the realm rendered from `../loamz-deploy`'s template. `seed.py` makes people (ana is an account admin of the organization acme), `token.py` signs one in.

- **Data lives in an S3-compatible bucket** (`loamz-data`, one prefix per securable id): RustFS in development (`deploy/dev/compose.yml`, key `loamz-dev`), R2 for the live server; a folder store exists for tests only. Settings: `LOAMZ_DATA_BUCKET`, `_BUCKET_ENDPOINT`, `_BUCKET_KEY_ID_REF`, `_BUCKET_SECRET_REF`, and how machines are given access, one of `_BUCKET_STS_ENDPOINT` (STS `AssumeRole`; `_STS_REGION` default `us-east-1`, `_STS_ROLE_ARN` only for AWS) or `_BUCKET_ISSUER_TOKEN_REF` (a Cloudflare token that can issue temporary credentials). `LOAMZ_DATA_SERVERLESS_TOKEN_REF` and `LOAMZ_DATA_SERVERLESS_ENDPOINT` (the deployed Modal URL: with the token, the Compute page can create serverless SQL warehouses without typing it). Serverless (Modal) cannot reach a local RustFS, so `scripts/dev.sh` leaves it off. Live tests: `LOAMZ_TEST_STS_ENDPOINT=http://127.0.0.1:9000 cargo test -p loamz-lake --test sts_live -- --include-ignored` (RustFS), `LOAMZ_TEST_R2_DIR=~/.config/loamz/r2 cargo test -p loamz-lake --test r2_live -- --include-ignored` (R2; keys in `~/.config/loamz/r2/`).
- **Secrets** are OpenBao's and nowhere else (`kernel/secrets.rs`: the `SecretStore` contract, `OpenBao` over its KV v2 HTTP API). Settings name a secret by reference `path#key` (`*_REF`), never by value or file; `Settings::resolve` reads them all once at start into `Secrets` (no `Debug`) and `App::new` takes that. The only file is the server's own login: `LOAMZ_DATA_OPENBAO_ADDR` with `_TOKEN_FILE` (development) or `_ROLE_ID` and `_SECRET_ID_FILE` (an AppRole); `_MOUNT` defaults to `secret`. Live test: `LOAMZ_TEST_OPENBAO_ADDR=http://127.0.0.1:8200 cargo test -p loamz-data-server --test secrets -- --include-ignored` (token and AppRole, deny by default).
- **People and organizations** are Keycloak's. `kernel/directory.rs` is the `Directory` contract (create an organization, ensure a person, add a member) with `Keycloak` as its adapter, a service account (`LOAMZ_DATA_DIRECTORY_SECRET_REF`, client `loamz-data-directory`, which needs the realm-management roles `manage-users` and `manage-realm`). The installation's admin holds the client role `platform-admin` on `loamz-data`; `POST /api/v1/orgs` makes an organization with its first admin, and an account admin adds people with `POST /api/v1/orgs/{org}/people`. A new person gets a temporary password, shown once. The dev realm (`deploy/dev/realm-loamz-dev.json`) has the user `admin` / `admin` (changed at first sign-in); production needs the role and the directory roles added to the realm template in `loamz-deploy`.
- **Service principals** (`governance/workspaces/principals.rs`) are identities of one workspace that are not people: made by a workspace admin, signed in with a token `lsp_…` we issue (shown once, only its hash kept; the `Identity` extractor in `governance/context.rs` checks it), assigned to their workspace as a user, named `sp:<id>` in grants, and `Identity.confined_to` makes any other workspace "not found". A catalog belongs to exactly one workspace (`securables.workspace_id`); a workspace that owns catalogs cannot be deleted.
- `server/serverless/modal_app.py`: the serverless SQL endpoint (Modal; `modal deploy`, secret `loamz-sql` holds the token; stops itself a minute after its last call; the server never starts it for a statement: a stopped warehouse refuses work (`409 … is stopped. Start it first.`) until an admin starts it, and the UI offers Select compute / Start and Close; pinned to a region near the bucket (`LOAMZ_SQL_REGION` at deploy, default ap-southeast: the bucket is in APAC, and an Iceberg read is several round trips, so distance multiplies); `scripts/serverless-close.sh` stops it now). Tools venv with DuckDB 2.0 and Modal: `~/.cache/loamz/modal-venv`. `scripts/iceberg_seed.py` makes and fills a table the way any DuckDB client does. `scripts/nyc_week.py` copies one week of NYC yellow taxi trips (3 to 9 March 2025, 934,685 trips, 18 MB) from a folder of Parquet files on an S3 endpoint into a workspace as `nyc.main.yellow_trips`, through the catalog; the dev copy is in Spike, owned by ana.

## Rules

- Services form one line: audit < orgs < workspaces < iam < catalogs < volumes < tables < compute < queries < lifecycle. A service uses only those before it. `server/server/tests/layering.rs` checks this, and that `model.rs` files are pure.
- Data depends on no Agents code, in Rust or in the web app: Agents is a customer of Data's public API. The only link is configuration (`LOAMZ_DATA_AGENT_CLIENTS`, names of clients). `layering.rs` fails if a manifest, a source file or `web/package.json` names an agents dependency.
- Only `iam::service` decides who may do what, using `kernel::authz` (Unity Catalog privileges and ownership). Nothing else reads grants. A job's own token (`jt_…`) is the person's rights narrowed to what the run declared, checked in the same place (`iam::require`), and only the file routes (`FileCtx`) accept one.
- A caller who may not see a thing gets 404, never 403. Every refusal is audited. SQL never says whether a table exists: missing and forbidden are the same answer.
- Every change and its audit entry are one database transaction (`audit::service::Uow`); each organization has its own hash chain.
- Erase and drop are durable tasks (lease, retry, verify, audit). Never a best-effort call.
- A statement is parsed (`compute/sql.rs`): one plain query, every table named `catalog.schema.table` and authorized (`SELECT`) before it is queued. DuckDB inside the sandbox is a second, separate lock.
- Run details recheck current access to inputs. If access is lost, history retains status and timings, and a direct submitter can still see their SQL; results, logs and errors stay hidden. Delegated submissions do not expose SQL in the restricted view.
- Compute agents connect out; the server never connects to a machine. An agent holds only its own secret (shown once, kept as a hash). A serverless target is the one exception: the server calls the provider's https endpoint, which takes SQL only, only over data classified `normal`.
- A person's token issued to a client named in `LOAMZ_DATA_AGENT_CLIENTS` (the agents server's, reached only by token exchange) is that agent acting for the person: `act` is not needed, and the pair gets what both may do. Deploy: `loamz-agents` client in the realm template (standard token exchange on; local: `deploy/dev/agents_client.py`).
- A machine never holds the bucket's key: a run is given credentials for exactly its tables' folders, read-only, for its time limit plus five minutes (a statement has no job token at all; only a job's volume files go through the API with one).
- Queued and running work is capped per organization (`LOAMZ_DATA_MAX_ACTIVE_RUNS`, default 32). Admission takes a database row lock so concurrent server instances respect the same cap. This is a safety ceiling, not billing or a storage quota.
- SQL is written once in the portable subset (TEXT ids, BIGINT numbers, `$1`, NOT NULL columns); every database test runs on SQLite and on Postgres.
- Errors are RFC 9457; the API is versioned (`/api/v1`); the OpenAPI document and the router must agree (a test checks it).
- No backward compatibility, and no stand-ins in the product: nothing that skips real sign-in, and no authorization from the environment. Delete old code instead of shimming.
- Never commit secrets. Pushes and releases are done by the owner.

## Commands

- `make check`: fmt, clippy, tests on SQLite, web types and tests. PostgreSQL tests create databases and do not remove them: use a throwaway instance, then `LOAMZ_TEST_POSTGRES_URL=postgres://data:data-dev-only@127.0.0.1:55434/data cargo test -p loamz-data-server -- --include-ignored`.
- The local stack: `docker compose -f deploy/dev/compose.yml up -d`, then `deploy/dev/seed.py` (passwords go to `.dev/accounts.json`, never printed).
- Sandbox pieces, once per machine: `scripts/fetch-runsc.sh` and `server/runner/rootfs/build.sh`. gVisor tests are ignored by default; set `LOAMZ_RUNSC` and `LOAMZ_ROOTFS` and run `cargo test -p loamz-runner --test gvisor -- --ignored --test-threads=1`. Memory and process limit tests require cgroup enforcement, not `LOAMZ_ROOTLESS`.
- Web: `cd web && pnpm install && pnpm test && pnpm build`; `scripts/dev.sh` runs the server and the app; `web/scripts/e2e.sh` is the browser test (real sign-ins, a real agent; needs Python Playwright in `PLAYWRIGHT_PY`, the release builds of the server and the runner, and the sandbox pieces above).
- `scripts/compute-smoke.py`: a query and a job, end to end, without a browser. With `REMOTE=user@host KEY=…` the agent runs on that machine instead.
- `scripts/budget.sh`: idle memory under 30 MB, ready under 200 ms. `scripts/smoke.sh`: the governance path with `curl`.
- `cargo zigbuild --release --target aarch64-unknown-linux-gnu.2.35 -p loamz-data-server -p loamz-runner`: the ARM builds.
