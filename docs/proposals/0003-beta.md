# Proposal 0003: the beta

Status: agreed 13 Nov 2026 (owner's decisions). Supersedes the plan section of the roadmap.

## Context

The beta is nearly feature-complete, not a minimum; smaller improvements wait until after it. It sells **governance only**: a customer
points us at their own bucket and their own machines (a laptop, a cloud VM, a VPS, or a Modal account) and pays for those themselves.
The beta group is the owner plus fewer than three others, by invitation, with billing and support done by hand.

## Scope

**In the beta:** everything in the roadmap's phases 1 to 4 that a customer relies on, and the three things the decisions add:

1. **Their storage.** A store per storage location (S3, R2, MinIO or RustFS in the customer's account), a write-only way to give us
   their keys (kept in OpenBao), external objects, storage grants, and a defined behavior when access is revoked.
2. **Their compute.** An installer for a customer's machine (runner, gVisor, worker, DuckDB library) and a guide for a Modal account.
3. **Speed, bringing data in and keeping it in shape:** a warm engine under 0.5 s, results streamed as Arrow, file pruning,
   import (file, S3, URL) through compute, compaction and snapshot expiry.

Plus: job schedules and alerts, search, a SQL connection for BI tools (Arrow Flight SQL), abuse limits, production deployment, the AI
phase (functions as agent tools, agent sandboxes, MLflow), and user documentation for all of it.

**After the beta:** SCIM and enterprise SSO extras, SOC 2 and data residency, hybrid mode, sharing across organizations, a free tier,
a Terraform provider, cost budgets, materialized views, data quality checks, lineage, traces, audited support access.

## How a wave runs: write everything, then verify once

Building and testing one feature at a time costs far more time than it saves, because every cycle pays for compile, start-up and
reading the failure again. So each wave has four steps:

1. **Write.** Every owner writes all the features of the wave against the agreed contracts. Nothing is compiled or tested in this step
   beyond what the editor shows, so the whole wave is written in one stretch.
2. **Integrate once.** The lead merges every branch of the wave into one integration branch and runs one pass, under the shared lock:
   format, clippy, the SQLite and Postgres suites, the worker checks, the release builds.
3. **Fix in one batch.** All failures are collected from that one pass, sorted, and fixed together by their owners.
4. **Prove.** One run of the benchmark, the browser flows and the security review round on the fixed result, then the wave's gate.

Contracts (OpenAPI, schema, brief interfaces) are agreed before step 1, which is what makes writing without compiling safe. When a
failure shows that a contract was wrong, it is fixed in the contract first and then in every branch.

## The beta gate

All of: the speed gate; a fresh server deployed from the playbook passes the e2e flow; backup, restore and the WAL check pass on it;
a stranger installs a machine on a clean VM and queries a customer bucket; two review rounds in a row with no open finding; an upgrade
from a database made at the start of the beta works; every feature has a documentation page that was run; the owner's dry run.

## How the team works

1. **One owner per path.** Each workstream owns its directories; shared files (`specs/data/v1/openapi.yaml`, `migrations/0001_init.sql`,
   `Makefile`, `Cargo.lock`) change only in clearly marked sections, and the lead resolves any collision at merge.
2. **Contracts first.** Before code that touches the API or the schema, the agent posts the OpenAPI and schema change in its notes and
   the lead agrees it, so no two branches invent the same thing twice. Until the freeze, `0001_init.sql` is edited in place; after it,
   only new migrations are added.
3. **Only the lead merges to `main`.** A branch reaches `main` through the wave's integration pass: `make check`, the Postgres suite and
   (for the worker) `make check-worker` pass, and its "done when" is shown, not claimed. The lead verifies claims before merge.
4. **One heavy build at a time.** Builds and tests take a shared lock (`scripts/heavy.sh`), so three agents cannot overload the machine.
   Nobody opens another worktree's folder in the editor, and nobody builds the worker except through `make worker`.
5. **Worktrees.** One branch and one worktree per task, cut from `main`, merged back by the lead and then removed.
6. **Limits are planned for.** Codex has the smallest budget: its tasks are few and high-leverage, each with a notes file so a task
   can be picked up after a reset. Antigravity has the most, so the largest pieces go to it.
7. **Nothing unverified is trusted.** Every agent's report is checked by running the same command, not by reading the report.
