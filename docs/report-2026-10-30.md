## 1. What went wrong (failures first)

- **A real security bug, found by my own test and fixed.** After dropping a schema, the volume inside it could still be
  downloaded until the task ran, because only the dropped entry was hidden, not what is inside it. Now an entry whose
  ancestor is being dropped is "not found" (`catalogs::service::target`). Covered by `drop_is_a_durable_task`.
- **A wrong expectation in my tests, corrected on purpose.** A member without grants at the tenant's root got 404 from
  admin endpoints (erase, audit); they now get 403, because everyone knows their own tenant exists. Everything else
  stays 404 for things you may not see.
- **First launch of a fresh binary took about 1 s to become ready here; every later launch took 23 to 33 ms.** I believe
  it is the first execution of a new file on this WSL machine, not the server (the server's own log says ready 15 to
  20 ms after start). Not proven; check on the real edge box.
- Nothing is failing now. `cargo fmt --check` and `cargo clippy --workspace --all-targets -- -D warnings` are clean.

## Addendum (2026-10-29, owner awake): gVisor and an S3 filesystem, run for real

Verified on this machine (x86_64 WSL2):
- **gVisor.** `runsc` 20260126.0 (SHA-512 checked) ran real Python from the runner's own config: output returned, root
  filesystem read-only, writes only through `/workspace`, no network, an infinite loop killed on time with no container
  left behind. `LOAMZ_RUNSC=... LOAMZ_ROOTFS=... LOAMZ_PLATFORM=ptrace LOAMZ_ROOTLESS=1 cargo test -p loamz-runner --test gvisor`: 5 passed.
  `systrap` cannot start on WSL2 (it works on the Oracle server); `ptrace` does. **Limits, verified as root** (owner ran
  the tests with sudo; rootless `runsc` ignores cgroups, so there they skip): memory: a 64 MB allocation under a 256 MB limit
  works (control), 900 MB is killed (exit 137). Processes: 20 forks work under `pids.limit` 256 (control); a fork bomb ends with
  the sandbox killed whole (exit 2, no output) and nothing left behind (`runsc list` empty, 0 stray host processes).
  So the process limit is **fail-closed, not graceful**: gVisor makes a host thread per guest thread, and at the limit it
  cannot make another, so `fork()` is not given an error, the run dies. Output of a run that hits it is lost.
- **SeaweedFS S3 through a FUSE mount** (a throwaway SeaweedFS 4.48 container with test credentials, `rclone mount` with
  `--vfs-cache-mode full`, volumes folder on the mount): the smoke script passes end to end (upload, download, reader refused,
  erase, drop, audit), the 14 SQLite API tests pass, and a file written through the mount was read back from SeaweedFS itself.
  This confirms "a volume is a POSIX path": no S3 code was needed.
- On the mount, 4 of 5 file tests pass. `a_symlink_planted_in_a_volume_is_never_followed` fails in its own setup (an S3
  mount cannot create a symlink: I/O error), so on that backend the attack cannot be set up at all. Not a hole, but the test
  is skipped there in effect.
- Not tested: speed on S3-backed volumes, large files, concurrent writers on the mount, B2/R2, an NFS mount.
- The throwaway container and the mount were removed afterwards.

### gVisor on the Oracle server (aarch64, root, default `systrap` platform), 2026-10-29

Ran the same five tests (`runsc` 20260126.0 aarch64, checksum checked; a `python:3.12-slim` arm64 root filesystem; the test
binary cross-built here and copied to `/tmp`). Everything was removed afterwards; no service was touched; the load stayed
near 0.1 throughout. 5 of 5 pass:
- code runs, root is read-only, output only through the workspace, no network, hard kill leaves no container: pass.
- **Memory:** 64 MB under a 256 MB limit works; 900 MB is killed (exit 137). Same as `ptrace`.
- **Processes:** the control (20 forks) works. Under `systrap` a fork bomb does **not** die as it does under `ptrace`; it
  **stalls** (50 forks in 1.6 s, then nothing), and the run's clock kill ends it, with nothing left behind. So the limit
  contains the bomb either way, but a run that hits it ends by timeout, so give runs a short timeout.
- To bound the risk on the live box, the bomb was capped at 2000 forks of 2 seconds each.
- The `systemd` "degraded" state on the server is from old failed units of the earlier gVisor spike (`run-u787` and similar),
  not from this run.

### Remote compute: Data and governance here, the job on Oracle (2026-10-31)

`scripts/compute-demo.sh` (remote mode). Governance and Data run on the laptop. `loamz-runner run-job` runs on the Oracle
server (`~/loamz-compute`: runner, `runsc`, a Python root filesystem; nothing else touched). The runner is given one
job (JSON on stdin) and talks to the **Data API only**, through `ssh -R` to the laptop's loopback, with the caller's token.
The token stays in the runner process; the code in the sandbox has no network and no credential.
- Verified: the input volume was read through the API, the code ran in gVisor with 1 CPU and 2 GB, the output was written
  back to a results volume through the API and read back, and the audit trail shows each read and write as the caller.
- **1 CPU is real:** two busy processes on Oracle's 2 cores used 1.01 CPUs of work in 6.1 s. **2 GB is real:** a 2.5 GB
  allocation was killed (exit 137). Output of a killed run is lost (buffered stdout dies with the sandbox).
- Not done: governance does not start jobs itself yet (no `/jobs` endpoint; the script plays that part), the token passed
  is the caller's own (it should be a short-lived, narrowed one), there is no queue and no more than one machine.
- With Data on Cloudflare, only `data_url` changes. Local dry-run (rootless `ptrace`) works too.
